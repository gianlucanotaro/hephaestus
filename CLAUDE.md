# CLAUDE.md — Hephaestus

macOS menu bar app, a FancyZones-style window manager for Mac. Splits every screen into window zones (default: left / 16:9 center / right) and snaps windows into them.

## Build & Run

No Xcode; only Command Line Tools are installed, so `xcodebuild` is unavailable. Use SwiftPM.

```bash
./build.sh                    # swift build -c release → build/Hephaestus.app (signed with "Hephaestus Dev" if present, else ad-hoc)
open build/Hephaestus.app     # LSUIElement app: menu bar icon only, no Dock icon
swift build                   # quick compile check
./test.sh                     # unit tests (Swift Testing; see Tests below)
pkill -x Hephaestus           # stop it
```

`build.sh` also builds the `hephaestus-cli` executable into `Hephaestus.app/Contents/MacOS/hephaestus-cli`, signs it before the app, copies `assets/AppIcon.icns`, and takes `CFBundleShortVersionString` from `Sources/HephaestusIPC/Version.swift`.

Run `./setup-signing.sh` once to create a local "Hephaestus Dev" certificate; `build.sh` then signs with it. Without it the build is ad-hoc signed, the signature changes every rebuild, and macOS forgets the Accessibility grant (System Settings → Privacy & Security).

## Stack

- Swift 6.2 toolchain, `swift-tools-version:5.9` (Swift 5 language mode), macOS 13+
- AppKit for the app shell, status item, and overlays; SwiftUI only for the settings window (hosted in `NSHostingController`)
- Carbon `RegisterEventHotKey` for global hotkeys (no extra permissions)
- Accessibility API (`AXUIElement`) for moving/resizing other apps' windows

## Layouts

- `Layout` (Codable): `id`, `name`, `kind` (`template`/`grid`/`canvas`), `zones: [RelRect]`, optional `rule`. `RelRect` is relative to the screen's `visibleFrame`, values 0...1, **origin top-left, y down** (file format only; `RelRect.resolve(in:)` converts to AppKit space).
- A zone is identified by its **`ZoneIndex`** (`Int`, position in `Layout.zones`). Zones are ordered left-to-right, ties top-to-bottom. Never key anything by zone name. Display name: `Layout.zoneTitle(index)` ("Zone N").
- `rule: .ultrawideThreeWay` marks the one non-relative layout ("Ultrawide 3-way", the default): center = `Prefs.aspect` at full height, 25/50/25 fallback on narrow screens. Its `zones` are only the nominal split. New non-relative behaviour = new `TemplateRule` case handled in `ZoneLayout.zones(layout:in:centerAspect:gap:)`.
- Built-ins (`LayoutTemplates.builtIn`, ids `builtin.*`) are generated by pure functions and are never written to disk. Custom layouts live in `~/Library/Application Support/Hephaestus/layouts.json` (`{"version":1,"layouts":[...]}`); a missing file is fine, a corrupt one is renamed to `layouts.json.corrupt`, invalid/duplicate layouts are dropped on load.
- `LayoutStore.shared` is the single source of truth for layouts: `all`, `layout(id:)`, `active`, `setActive(id:)`, `upsert`, `remove`, `importLayout(from:)`, `export(_:to:)`. It posts `LayoutStore.didChange` on any change (the menu and `WindowTracker` react to it). `active` (`Prefs.activeLayoutKey`) is now only the global FALLBACK layout for screens with no assignment.
- **Always go through the `ZoneLayout` entry points** — never read `LayoutStore.shared.active` in geometry/overlay/snap code:
  - `ZoneLayout.layout(for: screen)` -> the `Layout` in effect (per-screen assignment, orientation default, fallback; with "span" on, the representative screen's layout)
  - `ZoneLayout.zones(for: screen)` -> `[CGRect]` by `ZoneIndex`, with the layout's own gap (`effectiveGap`) and the span surface (`surfaceFrame`) applied
  - `ZoneLayout.selection(at:on:)` -> drag hit-testing with the same layout, gap and overlap policy that drew the zones
  - `ZoneLayout.allZones()` / `surfaceScreens()` / `surfaceScreen(at:)` / `surfaceOwner(of:)` -> which screens own a zone surface (every screen, or only the first when spanning)
  - `ZoneLayout.setLayout(id:for:)` -> assign a layout (maps to the surface owner when spanning)
- Pure geometry: `ZoneLayout.zones(layout:in:centerAspect:gap:)`, `selection(at:in:gap:edgeThreshold:overlap:)`, `boundingRect(of:in:)` all work on `[CGRect]` + `Set<ZoneIndex>`.
- Snap actions: `WindowMover.snapFrontWindow(to: ZoneIndex)` / `snapFrontWindow(slot:)` (eligibility-checked, tracker-registered). Anything else that puts a window into zones calls `WindowMover.snap(_:toAppKitRect:zones:on:from:)`, which moves AND registers with `WindowTracker`.
- New settings: add the key (and a registered default) in an `extension Prefs` in the feature's own file, and call its `register…Defaults()` from `Prefs.register()` (the ONE place defaults are registered; never inside a controller's `start()`).
- Global hotkeys: use `HotKeys.shared` only (`@discardableResult register(keyCode:modifiers:action:) -> UInt32?`, nil when the system refuses the combo; `unregister(_:)`). A second `HotKeys` instance would install a second Carbon handler that swallows the first one's events; the initializer is private.

## Subsystems

- **Per-screen layouts (`ScreenLayouts.swift`)**: assignments `[displayUUID: layoutID]` in UserDefaults (`NSScreen.displayUUID`, the single UUID scheme; `windowTrackerUUID` is an alias). Separate landscape/portrait defaults are pinned onto new displays by `ScreenLayoutStore.start()`. `ScreenLayoutStore.didChange` posts on any change; DragSnap, WindowTracker and LayoutIndicator observe it. No per-Space layouts (no public Spaces API). The "Layout" menu acts on the screen under the cursor.
- **Spacing and span (`ZoneSpacing.swift`)**: per-layout `Layout.gap` (built-ins use an override dict in UserDefaults), adjacent-highlight distance, and "span layouts across all screens" (zones over the union of `visibleFrame`s; the first screen owns the surface; rotation is disabled while on).
- **Editors**: `LayoutEditors.open(on:editing:)` is the router (grid layout or grid-shaped built-in -> grid editor; canvas -> canvas editor; anything else, e.g. overlapping Focus -> canvas copy); `GridEditor.open(on:)` / `CanvasEditor.open(on:)` start new layouts. Both plug into `LayoutEditorController` via the `LayoutEditing` protocol; pure models (`GridModel`, `CanvasModel`) hold all logic and are tested. The open-editor hotkey and the menu both use the router.
- **Window eligibility (`WindowEligibility.swift`)**: `WindowEligibility.canSnap(window:)` is THE gate (window-type policy + excluded-apps list). Used by DragSnap.begin, `snapFrontWindow`, keyboard nav move/expand, rotation (`RotationWindows.collect`) and new-window placement. Zone cycling only raises already-tracked windows and moves nothing. `ZoneResolution` picks one zone when zones overlap (smallest / largest / nearest center).
- **Window tracker (`WindowTracker.swift`)**: `WindowTracker.shared` maps AX windows to zones (+ layout id, home screen UUID, pre-snap frame, snapped frame), persisted best-effort. Every snap path registers via `WindowMover.snap` (drag, hotkeys, keyboard nav, rotation, auto-placement). It restores pre-snap size when a snapped window is dragged out, and re-applies windows on display changes, `LayoutStore.didChange` and `ScreenLayoutStore.didChange` (debounced 0.6s). Lookup order for "which zone is this window in": tracker record (same screen UUID + layout id, window still at its snapped frame) then frame overlap (`ZoneNavigation.currentZones`).
- **Keyboard navigation (`ZoneNavigation.swift`, `KeyboardNav.swift`)**: modes Direct (default: first/middle/last zone), Zone index (previous/next), Relative (nearest zone by arrow + expand span with extra Shift). Optional cross-screen movement. Modifiers are configurable and re-register on prefs change. Logic is pure and tested.
- **Rotation (`RotationPlan.swift`, `RotationMode.swift`)**: off by default; hold Option+X and press Left/Right to move all windows one screen over. A `CGEventTap` (fallback: NSEvent monitors) tracks the hold and swallows the keys. Windows keep their zone index; windows in no zone move proportionally and are untracked.
- **Zone cycling (`ZoneCycling.swift`)**: ⌃⌥ PageDown/PageUp activates the next/previous tracked window in the focused window's zone.
- **New-window placement (`NewWindowPlacement*.swift`)**: one `AXObserver` per app for window-created; moves the window to the app's last zone (default on) or the cursor's screen (default off); gated by `canSnap`.
- **Layout hotkeys (`LayoutHotkeys.swift`, `LayoutHotkeyActions.swift`)**: numbers 0-9 per layout (one map in UserDefaults), ⌃⌥⌘0-9 applies to the cursor screen, ⌃⌥⌘E opens the editor, optional zone flash.
- **Wheel + indicator (`LayoutCycling.swift`, `LayoutIndicator.swift`)**: optional mouse-wheel layout cycling during a snap-drag (a scroll-only event tap exists only while dragging), and a name popup on any effective-layout change.
- **CLI**: `hephaestus-cli` talks to the app over a unix socket (`~/Library/Application Support/Hephaestus/cli.sock`, 0600, peer-uid checked, one JSON line each way). Protocol/parser/render code is in `HephaestusIPC`; app side is `CLIServer` (socket) + `CLIHandler` (logic with injected stores). New command = `Request` case + parser + handler + tests.
- **Tests**: `./test.sh` only. Anything involving AX, event taps, overlays or real screens is not unit-tested; keep logic in pure functions.

## Settings architecture

- **Tabs** (`SettingsView.swift`): General (launch at login, Accessibility status, about), Activation, Layouts, Windows, Appearance, Shortcuts. Each setting appears in exactly ONE tab; split a section view (like `WheelCycleSetting`, `SpanScreensSetting`) rather than showing a control twice.
- **Key coverage**: `SettingsCatalog.exposed` maps each UserDefaults key to its tab, `internalKeys` lists keys deliberately without a control. `SettingsCatalogTests` fails if a registered default is in neither.
- **Adding a setting**: key + registered default in the feature's `extension Prefs` (called from `Prefs.register()`), a control in the matching tab (section view), the key in `SettingsCatalog.exposed`.
- **Adding a hotkey**: add a `ShortcutID` case and a `ShortcutSpec` in `ShortcutSpecs.all` (key-code key + modifiers key + default; `.single` = full shortcut, clearable via key code -1; `.group` = fixed keys, modifiers recorded; `.rotation` = one modifier). Read it with `ShortcutStore.read(id)` in the controller (re-register when it changes; controllers observe `UserDefaults.didChangeNotification`), add a `ShortcutRow(id:)` in the Shortcuts tab, and an `active` rule in `ShortcutStore.entries` so the duplicate checker knows when it is in effect. New key-code keys need a registered default equal to the old fixed key; copy shared legacy values in `ShortcutMigration.plan`.
- **One modifier type**: `HotkeyModifiers` (Carbon mask option set, stored as Int). `HotKeys.shared` records refused combinations in `failures` (UI warns); `setSuspended(true)` releases all combos while a recorder listens (`ShortcutRecording.isActive` also quiets the rotation tap).
- **Launch at login**: `SMAppService.mainApp` behind `LoginItemService`; `LaunchAtLoginState.make` is the pure status mapping. Disabled with an explanation when not running from a `.app` bundle.

## Conventions & Gotchas

- **Two coordinate spaces.** AppKit (`NSScreen`) is bottom-left origin; Accessibility is top-left origin relative to the primary screen. Zones are computed in AppKit space (overlays use them directly); convert with `ZoneLayout.toAX` only when calling AX. Mixing them up puts windows on the wrong side/height.
- Zones are computed from `screen.visibleFrame` (excludes menu bar/Dock), so the "16:9" center is 16:9 of the usable height.
- AX resize is done size → position → size because some apps clamp size based on the screen they currently sit on.
- Mid-drag layout changes: `DragSnapController` rebuilds the overlay on `ScreenLayoutStore.didChange`; unsnap-on-drag happens once, when the drag is first recognised as a window move.
- Menu-triggered snaps are delayed 0.15s so the previously active app becomes frontmost again.
- Settings are `UserDefaults` keys in `Prefs`; add new ones there with a registered default.
- macOS sees one display, so menu bar/Dock/Spaces are shared across zones and fullscreen takes over the whole display. That is a known limitation of the zones approach.
